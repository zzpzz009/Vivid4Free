# 外壳契约改造：体量与验收

本次目标是固定现有 UI/宿主边界，便于独立测试与后续替换宿主。范围包括 22 个请求、2 个推送事件、默认 17860/17861 双端口 HTTP，以及 Electron 调用适配；不重写业务服务、不切换外壳。

## 体量与复杂度

整体属于中等规模、兼容验证要求较高的重构。通道数量有限，核心困难是保留返回联合类型、取消行为、事件退订、任务幂等与提交结果未知状态，以及两个端口不同的鉴权条件。

改造提交 `8d17144` 涉及 24 个文件，新增 1,526 行、删除 209 行。其中规范与清单 336 行，测试约 637 行，架构检查工具 222 行；生产代码约新增 327 行、删除 205 行。大部分增量用于固定和验证行为，未引入新的运行时依赖。

如按人工工程排期，建议为同等范围预留 1–2 人日梳理和接入、1–2 人日兼容验收；这是工作量估算，不是本轮实际耗时或交付承诺。新宿主实现、统一旧接口错误格式、正式签名安装器及多电脑回归应另行估算。

## 登录后真实验收（2026-10-25）

结论：契约与适配器的代码验收通过；本例未发现阻止本地主线合入的适配器回归。完整产品验收未通过，放大出图和运行包重新接入仍有下述既有阻塞。源码候选客户端版本为 0.7.1，使用现有 CF 0.3.2。

隔离候选使用独立 userData 和 28762/28763 端口，用户亲自登录后由应用正常恢复会话。目录选择器实际打开与取消均可用，但确认选择并成功接入未通过验证。随后直接调用未改动的运行时管理器校验现有目录，首次观察到的失败是 `custom_nodes/was-node-suite-comfyui/was_history.json` 文件大小不匹配；这不能证明其余文件均有效。

为继续验证日常工作区，在隔离 userData 中新建了指向现用 CF 的“已有安装状态”测试设置，复用已运行的引擎。这是人工准备的持久化安装夹具，绕过了首次导入完整校验，不能算作目录导入成功、ZIP 安装或新电脑验收。未为修复校验修改 CF、模型或私有工作流。
