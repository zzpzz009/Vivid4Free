更新时间：2026-10-20。此文档是本次账号对接的问题与配合事项唯一汇总入口；随实测持续更新。

## 1. 目标与边界

客户端共用 `https://www.vividai.com.cn/new-api`，参考项目为 `G:\Agent\Vivida4free\VividAI-Render-Upscale`。先接现有账号密码登录、读取账号资料、恢复会话和退出。本地CF出图不扣额度，保持本地图库，不把图片自动上传账号中心，也不把云端预占/结算链路搬过来。

用户已在本机交互测试版自行输入账号；本轮随后验证了真实资料刷新、重启恢复、退出和退出后重启，用户再次手动登录后也恢复成功。未读取或记录其密码、令牌，尚未交接自动化专用测试账号。真实令牌到期与服务端撤销后的拒绝行为仍待验证。登录是否应成为本地生成的强制条件、离线可用时间和设备授权策略，尚未定义，本轮不新增这类限制。

## 3. 多电脑分发与白名单评估

2026-10-20补充：用户在新启动的交互测试客户端反馈正常登录成功。此结果覆盖本机现有密码兼容路径；尚不能据此认定浏览器回调已放行、原生PKCE已经支持，或多台电脑和完整会话生命周期都已验收。

`127.0.0.1`始终表示当前用户自己的电脑，相同固定回调地址可在多台电脑复用，无需逐台登记公网IP。但固定端口可能被其他程序占用；Origin/CORS只能约束网页来源，不能证明原生程序身份。现有精确callback白名单无法直接覆盖随机端口。

结论：白名单可以继续承担回调地址约束，不能单独作为分发客户端的认证方案。安装器内的固定client secret也无法保密。PKCE保护本次授权码的兑换，仍不证明安装包未被修改；软件权限和会话撤销必须由账号中心依据正式策略处理。

| 方案 | 分发适用性 | 当前状态 |
| --- | --- | --- |
| 现有密码登录API，由主进程HTTPS请求 | 不依赖逐台IP或浏览器回调，适合作为现有系统的兼容接入 | 本机真实登录、资料、恢复、正常退出已测；角色/MFA、到期撤销、正式原生使用策略和跨电脑仍待确认 |
| 固定loopback回调+现有网页handoff | 地址可复用，但有端口冲突；仅加白名单不足以解决code截获和native身份绑定 | 不作为未经验证的正式多机方案 |
| 系统浏览器+loopback随机端口+PKCE S256 | 推荐长期原生登录；不必逐台登记地址，服务端仅对loopback端口允许例外 | 服务端需登记public native client并提供完整PKCE契约；不得假设现有exchange已支持 |
| 自定义协议回调+PKCE | 无需监听本机HTTP端口；要处理协议注册、唤起和拦截风险 | 候选替代方案，当前安装器尚未登记协议 |
| Device Authorization Grant | 不依赖回调，但增加设备码输入和轮询 | 仅在服务端明确提供时采用；具备浏览器的桌面端优先原生浏览器授权方案 |

标准依据：[RFC8252 §7.3、§8](https://www.rfc-editor.org/rfc/rfc8252.html)说明原生loopback端口例外、public client与PKCE要求；[RFC7636](https://www.rfc-editor.org/rfc/rfc7636.html)定义S256兑换校验；[RFC9700 §2.4](https://www.rfc-editor.org/rfc/rfc9700.html)禁止OAuth密码授权；[RFC8628](https://www.rfc-editor.org/rfc/rfc8628.html)定义设备码流程。密码登录接口存在不等于它已经是OAuth原生授权流程；如果后端把它作为OAuth密码授权，不能作为长期推荐方案。

## 4. 用户系统一次性配合清单

以下集中列出依赖，按“现有兼容接入必需 / 原生正式方案 / 产品策略”分组，不要求扩大已有网页白名单或替换现有Casdoor回调。

### 4.1 现有接口联调必需

1. 本机用户自行登录的正向联调已完成，无需把其密码交给Agent。后续如需无人值守回归，请另提供专用测试账号和已开通的软件用户角色，不使用真实客户账号；密码通过安全方式交接，不写本文档或Git。确认`user`/`company_admin`角色、无公司/停用/撤销场景的响应。
2. 确认`POST /auth/password-login`允许原生客户端使用；约定需要的客户端标识、MFA、限流与错误码。不要以删除全局Origin检查的方式解决桌面接入。
3. 确认`GET /account/context`、`POST /auth/logout`、令牌到期、刷新或重新登录、设备会话撤销的正式契约。返回值与参考前端的`token`、`profile`、`availability`等字段核对。
4. 确认本地免费客户端的账号权益与云端计费隔离：密码登录及资料查询不能扣额度；本地出图不要求云端虚拟Key，不调用workspace-operations。
5. 明确原生主进程不手填网页Origin时的允许规则；如需独立native路由或标识，请提供正式接口，不要求客户端伪装已有网页域名，也不扩大web CORS到任意来源。请一起提供401/403/429、停用账号、MFA、网络重试和服务器注销失败的响应示例，敏感字段脱敏。

### 4.2 推荐原生正式登录方案

1. 登记独立public native client标识，例如`vivid-desktop`，不分发client secret。
2. 提供授权码+PKCE S256：code绑定client、精确redirect URI、challenge、用户和短时单次事务；兑换必须验证verifier，失败重放拒绝。
3. 若采用loopback，仅允许`127.0.0.1`（可单独支持IPv6 loopback）和约定callback路径，对端口采用RFC8252的原生应用例外；不允许任意HTTP主机/路径/全站Origin通配。保留现有web来源与回调校验。
4. 明确state回传、防CSRF、授权取消、超时、code过期/重复使用、令牌轮换和服务端注销的状态与错误响应。
5. 若改用自定义协议或设备码，先给出对应正式端点、回调/协议注册规则、有效期、轮询间隔和拒绝/慢询响应，再接客户端；本轮不虚构这些API已存在。
6. 一次性明确负责修改的账号服务/Casdoor部署、授权与兑换端点、client配置负责人、是否需要部署重启以及测试环境地址。Casdoor到账号服务的既有回调与账号服务到桌面客户端的回调是不同层，不直接替换现有网页`CASDOOR_REDIRECT_URI`。

### 4.3 产品策略待确认

- 是否必须登录后才能本地生成；若要求，账号撤销如何传达至离线电脑。
- 离线可用范围、过期与重新验证策略；是否需要设备绑定、设备数量限制及本地免费版独立授权。
- 本地记录与云端账号之间是否需要同步；默认仅本地保存，不自动上传图像。

## 5. 客户端实施与验收

已实现客户端兼容路径：主进程限定账号中心地址与可信IPC发送方，密码仅用于当次HTTPS请求，令牌由系统安全存储保护；界面展示登录/资料/网络异常状态，退出清除本机会话并尝试服务端注销。密码提交结束或关闭面板后清空输入。网络异常时提供退出本机登录。令牌恢复后必须再次向服务器验证，不把本机缓存或仅解码JWT当成服务端身份验证。

`signed_in`只表示服务器接受凭据并返回具有身份字段的资料，不表示软件角色、设备授权、离线权益已经开通；角色/权益以第4节正式契约为准。当前未新增强制登录门槛。Agent能力字段`account: deferred`仍表示整体账号联调未完成，不是用户登录状态；账号状态只通过受限主进程桥接读取，不向Agent提供账号令牌。

本轮桌面桥接约定：`accountStatus()`、`accountLogin({username,password})`、`accountRefresh()`、`accountLogout()`返回脱敏快照；`accountResetPassword()`只打开经主进程校验的官方HTTPS找回入口。快照仅含`status`（signed_out/checking/signed_in/unavailable）、`profile`、`persistent`、`message`、`retryAfterSeconds`和`lastCheckedAt`，不包含token或虚拟Key。签入必须经过服务端账户资料确认。无安全持久化能力时仅内存会话并明确提示，不明文降级。

| 场景 | 当前状态 |
| --- | --- |
| 接口可达、匿名拒绝、loopback白名单现状 | 已实测，见第2节 |
| 输入校验、令牌不返回渲染页、不明文落盘、401与网络错误区分、退出竞态及限流 | 相关桌面测试36项、前端测试140项通过；成功会话测试使用显式fixture，非真实账号验收 |

| Windows系统加密与真实会话持久化 | safeStorage往返、真实密文容器结构及跨重启恢复已验；不导出或读取明文令牌 |

## 6. 后续处理方式

账号系统按第4节一次性回复接口契约、策略与测试条件；客户端把实测阻塞追加到第2节，并将第5节逐项更新。没有通过的场景保持未验收，不把单测、mock或预留按钮算作线上接入成功。
